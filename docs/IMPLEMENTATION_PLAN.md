## 1. 交付目标

一个新后端工程、一个新前端工程、一套平台数据库。管理员与教师在统一后台管理账号、班级及考试系统的试卷、编辑和发布。学生使用同一账号登录，选择 SAT 或 SHSAT 后直接进入对应学生首页；SAT/PSAT 在 SAT 系统中按试卷类型和评分规则区分。旧系统最终只作为迁移来源和历史备份，不在新平台的日常调用链中。

首期以**模块化单体**实施：公共能力只实现一次，考试规则按类型模块隔离。新增类型要增加自己的模块和必要的专属表，但不重建身份、班级、试卷版本、发布目标或作答身份体系。暂不建设可热插拔的运行时插件框架。

## 2. 工程骨架

目标目录结构（已实现目录与计划目录并列）：

```text
unified_exam_platform/
├── backend/                 # 一个 Spring Boot 工程，按业务模块分包
│   └── src/main/java/.../
│       ├── identity/        # 登录、账号、角色、服务端授权
│       ├── classroom/       # 班级和多班级成员关系
│       ├── catalog/         # 考试类型注册、可用能力查询
│       ├── paper/           # 试卷版本、材料、题目及公共元数据
│       ├── release/         # 考试发布、目标班级、参与资格
│       ├── attempt/         # 作答生命周期、呈现题目、答案持久化
│       ├── result/          # 成绩持久化、报告访问控制
│       ├── asset/           # 文件元数据与存储接口
│       ├── audit/           # 关键管理操作审计
│       └── examtype/
│           ├── satpsat/     # SAT/PSAT 共享的模块与编辑逻辑
│           └── shsat/       # 新版 SHSAT 专属规则与题型
│   └── src/main/resources/db/migration/ # 新库自身的 Flyway 版本化迁移
├── frontend/                # 一个 Vue 3 / Vite 项目
│   └── src/
│       ├── app/             # 路由、登录态、布局、API 客户端
│       ├── platform/        # 账号、班级、选考试、公共发布组件
│       └── examTypes/
│           ├── satPsat/     # SAT 工作区内的 SAT/PSAT 项目组件
│           └── shsat/       # SHSAT 管理、编辑、考试与报告页面
├── deploy/                  # 环境配置示例、部署与回滚说明
└── docs/                    # 架构、数据库、接口和实施文档
```

后端沿用现有团队熟悉的 Spring Boot / Java 技术栈，前端沿用 Vue 3 / Vite；新前端建议使用 TypeScript 管理跨模块契约。具体框架版本、构建工具和部署环境在工程初始化时固定，不在设计阶段追逐版本更新。后端初期保持一个工程和一个进程，避免只为模块划分引入多套构建和跨服务调用。

## 3. 功能边界

| 模块 | 平台负责 | 考试类型模块负责 |
| --- | --- | --- |
| 账号与权限 | 账号、密码、统一登录、角色、接口授权 | 不创建独立账号或签发独立登录令牌 |
| 班级 | 班级、多班级成员、教师管理全部班级 | 只接收统一班级 ID 和学生 ID |
| 试卷 | 类型编码、分组、版本、封存、资源引用、基础列表 | 具体试卷结构、编辑校验、题型配置和预览 |
| 发布 | 场次、时间、目标班级/学生、资格去重、状态 | 发布前的类型规则校验、类型专属场次参数 |
| 作答 | 资格检查、尝试次数、生命周期、答案保存、历史归属 | 计时/导航、自适应分支、题目呈现、提交规则 |
| 判分与报告 | 评分规则版本引用、结果保存、访问控制 | 原始分计算、量表换算、报告内容与专属分析 |
| 文件与审计 | 文件存储接口、操作记录 | 决定专属资源用途和业务内容 |

模块之间只通过清晰的服务接口传递全局 `user_id`、`class_id`、`paper_id`、`exam_id` 和稳定的 `exam_type_code`。控制器不直接查询其他模块的表；前端页面不直接拼装跨模块业务规则。数据库同处一个库并不意味着各模块可以任意写彼此的数据。

### 后端考试类型契约

首期只抽取三个确实共享的扩展点：

1. **试卷能力**：编辑数据校验、结构组装、发布前完整性检查。
2. **考试能力**：开始作答、确定实际呈现题目、保存进度、提交及类型专属时间/导航规则。
3. **评分能力**：按封存的试卷和评分版本判分，返回统一结果摘要与类型专属报告明细。

平台通过稳定的项目编码找到已注册的处理器。SAT 和 PSAT 是同一个 SAT 工作区内的两个项目，共用 SAT/PSAT 试卷与自适应实现，但保留各自的试卷、评分配置和历史项目编码。SHSAT 是独立工作区，拥有自己的题型与流程实现。不要做一个拥有几十个可选方法的万能 `ExamPlugin`，也不要在公共服务中用大量 `if (type == ...)` 分支实现规则。

### 前端考试类型契约

每个项目模块注册：项目编码、所属工作区、管理路由、试卷编辑页、发布参数页、学生考试页和报告页。公共路由负责登录、角色保护、工作区选择和布局。管理端和学生端只显示 SAT、SHSAT 工作区入口；SAT 工作区的试卷标记 SAT/PSAT，发布和计分按该标记加载对应规则。

前端只展示后端返回的已启用类型，并确认本地有对应页面模块；数据库插入一条 `exam_types` 记录不会自动产生可用的新考试流程。

### 关键调用链与 API 边界

| 操作 | 调用顺序与数据归属 |
| --- | --- |
| 编辑试卷 | 管理 API → `paper` 检查版本状态 → 对应类型模块校验内容 → `paper` 保存公共元数据与题目关联；已封存版本只能复制新版本 |
| 发布考试 | 管理 API → `release` 检查权限、时间和目标 → 类型模块校验试卷与专属参数 → 同一事务写入发布、目标和参与资格 |
| 开始作答 | 学生 API → `attempt` 检查登录、资格和次数 → 类型模块确定初始题目/阶段 → 写入作答与实际呈现题目 |
| 提交和判分 | 学生 API → `attempt` 校验状态与时间 → 类型模块校验答案并评分 → `result` 保存总分和类型明细 → 更新作答状态 |
| 查询报告 | 学生/管理 API → `result` 校验数据归属与角色 → 类型模块组装专属报告；只返回允许展示的答案和成绩 |

路由按资源分组：`/api/auth/*`、`/api/admin/users/*`、`/api/admin/classes/*`、`/api/exam-types`、`/api/admin/exam-types/{code}/papers/*`、`/api/admin/exam-types/{code}/exams/*`、`/api/student/exams/*`、`/api/student/attempts/*`。公共端点负责身份、归属和状态；类型专属编辑字段使用明确的版本化请求结构，由对应模块解析。学生试卷接口只返回题面与可见资源，绝不包含 `answer_key_json`、评分规则密钥或管理端字段。

## 4. 第一阶段：先完成基础框架

这一阶段的目标是形成可运行、可扩展的空平台，**不迁旧试卷、不复制旧页面**。

| 工作包 | 具体产出 | 完成标准 |
| --- | --- | --- |
| 工程初始化 | 一个后端工程、一个前端工程、配置模板、目录和模块依赖规则 | 本地可启动；项目结构与本文一致 |
| 数据库基线 | 新库版本化主数据 DDL：考试类型、用户、班级、多班级关系、审计事件 | V1 可初始化空库；后续核心业务表按模块追加版本 |
| 统一 API 约定 | 路由命名、统一错误格式、分页、时间格式、身份上下文与权限矩阵 | 前后端有可对照的接口契约；类型代码含义一致 |
| 身份框架 | 登录态、角色判定、禁用账号处理、统一账号 ID | 所有管理和学生路由都经过同一鉴权入口 |
| 类型注册 | 后端类型处理器注册、前端路由注册、数据库类型目录 | 未注册或停用类型不能创建新试卷/考试；历史可按权限读取 |
| 前端外壳 | SHSAT 后台风格的管理布局、登录页、学生选考试页、类型导航 | 可进入不同类型的占位入口，公共布局与登录态统一 |
| 基础运维 | 环境配置、文件存储接口、结构化日志、审计入口、部署说明 | 关键配置不写死；可定位一次请求及其操作者 |

第一阶段不先造完整通用试卷编辑器。当前公共编辑器提供分节、题目及类型 JSON 配置的基础管理；发布前的完整题型校验和正式考试页面由后续 SHSAT、SAT/PSAT 业务链验证和补齐。

## 5. 后续实施顺序

### 阶段 2：账号与班级形成首个完整业务闭环

- 后端完成用户新增、禁用、改密、角色校验；班级创建、停用、成员加入/退出与多班级查询。
- 前端完成管理员/教师账号页、班级页，学生登录与考试类型选择页。
- 明确并落地教师对试卷、发布、成绩的权限；当前已确认教师可以管理全部班级。
- **退出条件**：一个学生只有一个账号，可加入多个班级；教师可管理全部班级；服务端拒绝越权操作。

### 阶段 3：公共试卷、发布与作答骨架

- 完成试卷版本与封存、素材管理、考试场次、目标班级/个人、参与资格去重、作答状态、成绩记录的公共流程。
- 实现公共管理列表和发布表单骨架；发布前调用类型模块的完整性检查。
- 明确“发布后入班”规则，再确定参与资格生成时机；不在数据层预先写死一种策略。
- 当前已落地正式考试尝试、题目顺序、学生答案保存和可见总分；SHSAT 题型评分由 SHSAT 模块实现，其他考试类型只有模块声明支持后才进入学生待考列表。
- **退出条件**：以 SHSAT 的最小纵向链路从草稿试卷走到发布、学生资格、提交与结果保存；公共服务不包含 SAT/SHSAT 专属判断。阶段 4 再补齐 SHSAT 全部题型与页面。

### 阶段 4：迁移并完成新版 SHSAT 管理与考试流程

- 将独立新版 SHSAT 后台纳入统一平台作为 SHSAT 模块，保留原管理页视觉设计、导航和操作流程；复用统一账号、角色、班级、试卷/考试主数据与作答记录。
- 迁移试卷分组、Part/子题型、材料与图片、题目编辑、试卷导入导出与预览、评分档案、发布、监考、班级成绩、学生报告和错题任务；每项页面操作都必须连通当前平台 API，不能留下只显示的空壳按钮。
- 为旧 SHSAT 字段与当前规范化试卷表建立明确映射。扩展数据只落入 SHSAT 专属表；不要复制用户、班级、考试或题目主表。
- 按 [question-types.md](../../shsat_exam_system/new_system/docs/question-types.md) 盘点已支持题型和结构化答案契约，逐项迁入新模块；保留延时等专属配置。
- 页面与后端按模块接入，沿用可复用的原题型组件，但不复制一套登录、账号或班级实现。
- **退出条件**：原独立新版 SHSAT 的管理操作均在统一后台完成，并能完成创建/编辑试卷 → 发布到班级 → 学生作答 → 判分、监考与报告的关键流程；数据库迁移执行成功，主要功能完成接口与页面走查，旧版 SHSAT 不进入实现范围。

### 阶段 5：接入 SAT 与 PSAT

- [x] 将原 SAT 试卷编辑页面及 RW/Math 模块、题型、答案选项、材料编辑交互接入统一后台；写入统一试卷和题目主表，并保留 SAT 专属配置。
- [x] SAT/PSAT 计分表设置与 SAT 材料关联使用独立扩展表；模块/题目编辑通过细粒度接口更新，保持现有题目 ID。
- [x] SAT/PSAT 模块内提供班级管理入口并复用共享班级数据；从 SAT 与 SHSAT 顶栏移除独立 Classes 页面入口。
- [ ] 完成 SAT/PSAT 发布到班级、学生考试流程、自适应规则、断点续考、判分和报告的端到端迁移与验证。
- SAT、PSAT 注册为两个明确类型，内部复用共通逻辑；不能再通过总分推断类型。
- SAT/PSAT 共用 SAT 后台和学生入口，按试卷类型应用各自规则；发布时仍使用统一班级与资格体系。
- **退出条件**：同一个账号和班级可参加三种类型考试，类型规则、成绩和页面相互隔离。

### 阶段 6：旧数据迁移与切换

- 在业务规则和新功能稳定后，编写旧库数据迁移脚本：先账号/班级和人工审核映射，再试卷/资源/评分版本、发布、作答与成绩。
- 旧数据迁移需要可重跑、可对账和回滚；SAT/PSAT 的历史类型不能仅凭 1600/1520 总分猜测，无法确定的记录进入人工核对。
- 灰度切换管理端和学生端；稳定后停止旧系统写入，移除已被新系统替代的旧逻辑和页面。
- **退出条件**：新平台是唯一运行时数据源；账号、班级、三类试卷、考试和历史成绩均可追溯。

## 6. 工作依赖与开发顺序

```mermaid
flowchart LR
  A[基础工程与类型契约] --> B[账号与班级]
  A --> C[公共试卷与发布]
  B --> D[学生资格与作答]
  C --> D
  D --> E[SHSAT 完整流程]
  E --> F[SAT / PSAT 完整流程]
  F --> G[旧数据迁移与切换]
```

每个考试类型按“后台编辑 → 发布 → 学生作答 → 判分 → 报告”交付完整纵向功能，不以只做页面或只做数据库作为阶段完成。SHSAT 先行用于验证从现有后台参考中提炼出的公共能力；SAT/PSAT 再验证这些边界对自适应考试是否成立。需要修改公共契约时，先说明影响并更新数据库与接口文档。

## 7. 需要提前确定的决策

| 决策 | 最迟确定时点 | 对实现的影响 |
| --- | --- | --- |
| 新入班学生能否参加此前已发布考试 | 阶段 3 发布逻辑前 | 参与资格生成和补录时机 |
| 教师试卷编辑、发布、成绩查看权限 | 阶段 2 权限落地前 | 服务端授权矩阵与页面可用操作 |
| 首期是否纳入监考、错题重做、可下载报告 | 各类型模块排期前 | 对应业务模块、表和页面是否进入首期 |
| 账号冲突归并与密码策略 | 阶段 6 迁移前 | 人工审核流程和登录切换 |

当前阶段可先完成工程框架、稳定主键和类型契约，不必等待这些业务规则才开始设计；涉及发布资格和教师权限的功能开发必须依据最终决定。

## 8. 本计划刻意控制的复杂度

- 一个后端进程、一个前端项目、一套新数据库；不用多个考试服务长期互调，也不让新平台继续依赖旧库。
- 类型扩展采用明确的代码模块与必要的专属表；不用运行时插件市场、万能 JSON 试卷表或每类考试一套账号/班级。
- SHSAT 后台作为功能模板，页面按职责重新组织；迁入有效逻辑后及时清理旧逻辑，避免双份实现长期共存。
- 数据迁移在新业务模型稳定后进行；当前先确定目标结构和对应关系，不提前编写会反复推翻的迁移脚本。

## 9. 编码与维护规范

- 先遵循现有 SAT、SHSAT 项目的命名、格式、异常处理、日志和分层习惯；如果新旧项目约定不一致，在新平台内选定一套并保持一致。
- 代码按业务职责组织，函数和类保持单一职责；名称直接表达用途，调用关系清楚，避免缩写和隐式副作用。
- 只在有真实复用和稳定边界时抽象公共逻辑。考试类型之间相似但规则不同的部分，优先保留类型模块内的清晰实现，不为了“将来可能复用”建立泛化框架。
- 控制配置、接口、数据库表和抽象层数量；公共模块只包含已确认跨类型共用的概念，类型专属规则放入相应模块。
- 修改功能时清理已被完全替代的旧实现、无用分支和重复代码；保留历史兼容逻辑时说明其用途与移除条件。
- 非显而易见的业务约束写简洁注释；避免重复注释代码本身、超长控制器和把多个业务流程塞进单个组件或服务。
- 先完成一个端到端类型链路，再据实际差异调整公共契约；不提前实现没有当前需求支撑的插件系统、微服务拆分或通用工作流引擎。
